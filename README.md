# Auralis — Local-first AI meetings

Auralis is a complete, self-hosted AI meeting platform: native WebRTC audio/video calls, live
speech-to-text with faster-whisper, and genuine meeting summaries generated by a local Ollama
model. It uses no paid meeting SDKs, no cloud AI, and no API keys. Meeting recordings stay in the
browser; only metadata is stored in MongoDB.

## Features

- **Real calls** — native `RTCPeerConnection` mesh, shareable room links, camera/microphone
  toggles, screen sharing, participant presence, and host controls.
- **Live transcription** — browser audio is captured with an AudioWorklet, streamed as 16 kHz PCM16
  to the backend, and transcribed continuously by a local faster-whisper service. Segments carry
  timestamps, speaker attribution, provisional/final states, editing, search, copy, and TXT export.
- **Local AI summaries** — map-reduce summary of the real transcript with key points, decisions,
  action items, important moments, and open questions. Draft summaries update during the meeting;
  the final summary is generated automatically when the meeting ends. Failures are explicit and
  retryable.
- **Local recording** — the meeting gallery and mixed participant audio are recorded with
  `MediaRecorder` into WebM, with start/pause/resume/stop, elapsed time, IndexedDB persistence,
  in-browser playback, and download. The video blob is never uploaded.
- **Meeting workspace** — real-time chat, participant panel, host crown, meeting history, meeting
  detail tabs (summary, transcript, recordings), and searchable transcript/recording libraries.
- **Authentication** — email/password accounts with bcrypt and httpOnly JWT cookies, plus
  room-scoped signed guest access.
- **Dark, responsive UI** — built with Next.js App Router, React, TypeScript, Tailwind, and
  Zustand. The meeting interface is at `/meeting/[roomId]`.

## Architecture

```text
Browser (Next.js :3000)
  ├─ REST  ─────────────────────────────► Express backend :5000 ──► MongoDB :27017
  ├─ WS /ws (signaling + PCM audio) ────► Express backend :5000
  │                                           ├─ WS /ws/transcribe ─► faster-whisper :8000
  │                                           └─ HTTP /api/chat ────► Ollama :11434
  └─ MediaRecorder + IndexedDB (recordings stay here)
```

- **Frontend** — Next.js 16, React 19, TypeScript, Tailwind CSS 4, Zustand.
- **Backend / signaling** — Node.js, Express 5, `ws`, Mongoose, bcrypt, JWT, Zod.
- **Transcription** — Python, FastAPI, faster-whisper (`small` by default), WebSocket streaming.
- **AI** — local Ollama (`llama3.1:8b` by default), structured JSON validated with Zod.
- **Storage** — MongoDB for users, meetings, participants, chat, transcript segments, summaries,
  and recording metadata. No media blobs are stored in MongoDB.

### How the core pieces work

**WebRTC.** Every participant creates one `RTCPeerConnection` per remote participant (mesh, capped
at `MAX_PARTICIPANTS`, six by default). The newest joiner creates the offers; existing peers answer.
A participant can join without devices (receive-only), then enable media and renegotiate. Track
toggles use `replaceTrack`, so peers are not torn down. Screen sharing uses `getDisplayMedia` and
restores the camera track afterwards.

**Signaling.** The browser connects to `ws://localhost:5000/ws` and authenticates with a
`JOIN_ROOM` message. The server derives identity from the JWT/guest token, not from client-supplied
names, then forwards offers, answers, ICE candidates, chat events, and room-scoped state such as
recording/paused indicators. Heartbeats and reconnect backoff keep the session resilient.

**Live transcription.** Microphone audio is resampled by `/pcm-worklet.js` to 16 kHz mono PCM16 in
roughly 200 ms frames and sent over the signaling WebSocket. The backend opens an authenticated
WebSocket to the Python service, which transcribes overlapping 6-second windows with a 4-second
stride using word timestamps. Overlapping words are deduplicated; provisional hypotheses and final
segments are sent back with server-derived speaker identity. Typical end-to-end latency is a few
seconds.

**Summaries.** Transcript segments are timestamped and chunked for a map-reduce pass. The model
returns structured JSON, which is validated with Zod and gets one repair retry. Incremental drafts
are generated after the configured number of new final segments or elapsed time; the final summary
runs automatically after a meeting ends. If Ollama or the schema fails, the UI shows the real error
and exposes a retry path rather than inventing content.

**Recording.** A detached gallery canvas is rendered at 12 fps from local and remote video tiles and
explicitly captured with `canvas.captureStream(0)` + `requestFrame()`. Local and remote audio are
mixed with WebAudio into a `MediaStreamAudioDestinationNode`. The combined stream is recorded with
`MediaRecorder` (VP8/VP9 WebM with Opus, with MIME fallbacks), producing one-second chunks.
Recording state is shared with the room so every participant sees when a recording is active.
Completed blobs are stored in IndexedDB and can be played or downloaded; only file metadata is sent
to the backend. The recording canvas is kept attached to the document off-screen because Chrome
does not reliably deliver canvas frame timeslices for a detached canvas.

## Prerequisites

- **Node.js 20.9+** and npm
- **MongoDB 7+** running locally on port `27017`
- **Python 3.11** for the transcription service
- **Ollama** running locally on port `11434`, with the configured model pulled
- **Google Chrome** recommended (screen sharing and MediaRecorder support are best there)
- Optional: **ffmpeg** for inspecting downloaded WebM files or regenerating test fixtures

## Setup

### 1. Install JavaScript dependencies

```bash
npm install
```

### 2. Generate environment files and local secrets

```bash
npm run setup
```

This creates `.env` from `.env.example` (if missing), generates `JWT_SECRET` and
`TRANSCRIPTION_TOKEN`, and writes `backend/.env`, `frontend/.env.local`, and `transcription/.env`.
Never commit `.env` or the generated per-service files.

### 3. Start MongoDB

Use your platform's service, or run it directly:

```bash
# Windows (example data directory)
mongod --dbpath C:\data\db

# macOS (Homebrew)
brew services start mongodb-community

# Linux
sudo systemctl start mongod
```

### 4. Install and start Ollama

Install Ollama from <https://ollama.com>, then:

```bash
ollama pull llama3.1:8b
ollama serve
```

On Windows, if `ollama` is not on `PATH`, use the full executable path, for example:

```powershell
& "$env:LOCALAPPDATA\Programs\Ollama\ollama.exe" pull llama3.1:8b
& "$env:LOCALAPPDATA\Programs\Ollama\ollama.exe" serve
```

### 5. Install the Python transcription service

```bash
cd transcription
py -3.11 -m venv .venv                 # Windows
# python3.11 -m venv .venv             # macOS/Linux
.venv\Scripts\pip install -r requirements.txt   # Windows
# .venv/bin/pip install -r requirements.txt     # macOS/Linux
cd ..
```

The first startup downloads the faster-whisper `small` model and can take a while. The service
tries CUDA `int8_float16` when available and falls back to CPU `int8`; `/health` reports the active
device.

### 6. Start the application

Run the backend, frontend, and transcription service in separate terminals:

```bash
npm run dev -w backend
npm run dev -w frontend
npm run dev:transcription
```

Or start the backend and frontend together with `npm run dev`, then run
`npm run dev:transcription` separately.

Open <http://localhost:3000>. Check the full stack at
<http://127.0.0.1:5000/api/health> — it probes MongoDB, faster-whisper, and Ollama for real.

## Configuration

Edit the root `.env` and rerun `npm run setup` to regenerate the service files. Existing generated
secrets are preserved.

| Variable | Purpose |
| --- | --- |
| `MONGO_URI` | MongoDB connection string; defaults to `mongodb://127.0.0.1:27017/ai-meeting` |
| `JWT_SECRET`, `JWT_EXPIRES_IN` | Account session signing and lifetime |
| `GUEST_TOKEN_EXPIRES_IN` | Lifetime of room-scoped guest tokens |
| `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_WS_URL` | Backend REST and WebSocket URLs used by the browser |
| `NEXT_PUBLIC_ICE_SERVERS` | JSON array of ICE servers; STUN only by default |
| `OLLAMA_URL`, `OLLAMA_MODEL` | Local Ollama endpoint and model |
| `OLLAMA_TIMEOUT_MS`, `OLLAMA_NUM_CTX` | Model timeout and context window |
| `WHISPER_MODEL`, `WHISPER_DEVICE`, `WHISPER_COMPUTE_TYPE` | faster-whisper model/device settings (`auto` chooses CUDA then CPU) |
| `WHISPER_CHUNK_SECONDS`, `WHISPER_STRIDE_SECONDS` | Streaming window and stride (default 6 s / 4 s) |
| `TRANSCRIPTION_URL`, `TRANSCRIPTION_TOKEN` | Backend-to-transcription connection and shared secret |
| `SUMMARY_INCREMENT_SEGMENTS`, `SUMMARY_INCREMENT_MIN_MS` | Draft-summary cadence |
| `MAX_PARTICIPANTS` | Mesh size cap (2–8, default 6) |

## Privacy and data handling

- Audio and video travel directly between browsers over WebRTC. They are not sent to the backend,
  except microphone PCM sent to the local transcription service for speech-to-text.
- Recordings are created and stored in the browser's IndexedDB. The backend receives only file
  metadata (name, size, duration, MIME type). Use the download action to keep a copy; clearing site
  data removes the browser copy.
- MongoDB stores accounts, meetings, participants, chat messages, transcript segments, summaries,
  and recording metadata — no recording blobs.
- Speech-to-text and AI summarization run locally through faster-whisper and Ollama. No cloud AI
  service or paid API key is used.
- Transcription requires explicit consent before joining. Active recording and transcription are
  indicated in the meeting header.

## Troubleshooting

**The health endpoint reports a service as down.** Check that MongoDB, Ollama, and the transcription
service are running and that their ports match `.env`. The transcription model can take 30–90
seconds to load on CPU before it reports ready.

**`cublas64_12.dll` or CUDA errors.** faster-whisper attempted CUDA and fell back to CPU `int8`.
This is expected on machines without the CUDA runtime. To force CPU explicitly, set
`WHISPER_DEVICE=cpu` in `.env` and rerun `npm run setup`.

**Ollama returns “model not found”.** Pull the configured model: `ollama pull llama3.1:8b`, or set
`OLLAMA_MODEL` to a model you already have.

**Summaries time out.** A large model on CPU can take minutes. Increase `OLLAMA_TIMEOUT_MS`, use a
smaller model, or close other memory-heavy applications. The UI shows the error and offers a retry;
it will not display a fabricated summary.

**MongoDB connection refused.** Start MongoDB and confirm `MONGO_URI`. The backend exits at startup
if the database is unavailable.

**WebRTC connects locally but not across networks.** The default configuration uses public STUN
only and has no TURN relay. Peers behind symmetric NAT or restrictive corporate firewalls may fail.
Add a TURN server to `NEXT_PUBLIC_ICE_SERVERS` for production deployments.

**Screen sharing is blocked.** `getDisplayMedia` requires a secure context (HTTPS or localhost) and
a user gesture. Use Chrome and the latest build.

**Recording produces no media.** Use a current Chrome/Chromium-based browser, grant camera and
microphone permission, and keep the meeting tab rendering (the recorder also requests frames while
hidden, but browser implementations differ). The UI surfaces a real error if MediaRecorder emits no
data; retry after checking device availability. Recording is local to the browser profile that
created it.

**Ports are already in use.** Stop the previous process or change the matching port in `.env` and
the service launch commands.

## Known limitations

- **Mesh scaling.** WebRTC is peer-to-peer mesh: each participant sends media to every other
  participant. CPU and bandwidth grow quadratically, so the default cap is six participants.
- **No TURN server.** There is no relay fallback for restrictive networks. A production deployment
  should add TURN and HTTPS.
- **Speaker attribution is per browser participant**, not acoustic diarization. If several people
  share one microphone, their words are attributed to that participant.
- **Transcription is near-real-time, not instant.** Overlapping windows and model inference add a
  few seconds of latency, and CPU-only machines will be slower.
- **Summaries are model-generated.** Structured output and prompts discourage invented deadlines and
  assignees, but users should review action items and decisions.
- **Recordings stay in one browser.** There is no server-side backup; clearing site data or using a
  different browser/profile loses access to that local copy.
- **Single-node signaling.** Presence and signaling rooms are in memory. A backend restart drops
  active calls; clients reconnect, but a production deployment should use sticky sessions or a
  shared presence store.
- **Development servers use HTTP.** Camera/microphone work on localhost; remote access requires
  HTTPS. The provided configuration is intended for local and trusted-LAN use, not public
  multi-tenant hosting.
